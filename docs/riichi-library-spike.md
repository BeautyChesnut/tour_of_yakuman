# riichi 第三方库验证记录

本文记录 `riichi` npm 包作为第一版立直麻将算点库候选的初步验证结论。

## 结论

`riichi` 可以作为第一版候选库继续推进，但必须通过项目内 `scoring adapter` 接入，不能让 UI 或领域模型直接依赖它的字符串输入格式和原始输出。

建议策略：

- 第一版优先使用 `riichi` 负责基础和牌判断、役种、番数、总符数和基础支付。
- 项目 adapter 负责把项目数据模型转换为 `riichi` 字符串输入。
- 项目 adapter 负责把 `riichi` 输出转换为项目内 `ScoringResult`。
- 本场、供托、四家点数变化、结算后点数、点差由项目自己的 `settlement` 模块实现。
- 符数明细、宝牌分类展示和部分规则差异需要项目层补齐或明确暂不支持。

## API 形态

基础用法：

```js
const Riichi = require("riichi");
const riichi = new Riichi("112233456789m11s");
const result = riichi.calc();
```

输入使用紧凑字符串：

- `m`、`p`、`s`、`z` 表示万、筒、索、字牌。
- `1z` 到 `7z` 表示东、南、西、北、白、发、中。
- `0m`、`0p`、`0s` 表示赤五。
- `+<牌>` 可表示荣和牌。
- `+d<牌>` 表示宝牌，但这里需要传入实际宝牌，不是宝牌指示牌。
- `+r`、`+i`、`+w`、`+h`、`+k` 等用于立直、一发、两立直、海底/河底、岭上/抢杠等条件。
- 末尾数字可表示场风和自风。

## 需要 adapter 处理的点

### 宝牌指示牌转换

`riichi` 的 `+d` 输入接收的是实际宝牌，不是宝牌指示牌。

项目输入是宝牌指示牌、杠宝牌指示牌和里宝牌指示牌，因此 adapter 必须先将指示牌转换为实际宝牌，再传给 `riichi`。

### 宝牌分类展示

`riichi` 输出中宝牌统一为 `ドラ`，赤宝牌为 `赤ドラ`。

如果结果页需要区分：

- 宝牌。
- 杠宝牌。
- 里宝牌。
- 赤宝牌。

则项目层需要自行统计和展示这些分类。

### 本场和供托

`riichi` 不处理本场和立直供托。

项目必须在 `settlement` 模块中自行处理：

- 荣和时放铳者每本场额外支付 300 点。
- 自摸时每名对手每本场额外支付 100 点。
- 供托全部归单一和牌者。

### 四家点数和点差

`riichi` 输出基础支付信息，但不维护四家点数状态。

项目必须自行计算：

- 每家本局点数变化。
- 每家结算后总点数。
- 玩家之间点差。
- 最近一局结算记录。

### 符数明细

`riichi` 输出总符数，但不输出项目需要的符数明细。

如果第一版坚持展示符数明细，需要项目层补充符数明细计算；如果不补充，则需要调整 MVP 文案为“展示总符数，符数明细后续增强”。

### 规则配置

`riichi` 已提供：

- `disableKuitan()`：关闭食断。
- `disableAka()`：关闭赤宝牌。
- `disableWyakuman()`：关闭双倍役满。
- `disableYaku(name)`：禁用指定役。

但以下能力没有直接发现完整配置入口：

- 切上满贯。
- 双风雀头 2 符或 4 符切换。
- 关闭累计役满。当前项目第一版默认开启累计役满，因此不影响 MVP。

这些需要通过测试确认，无法覆盖时由 adapter 补齐或在规则中明确暂不支持。

## 小程序兼容性

`riichi` 是 CommonJS 包，不含原生模块，核心逻辑可以在 Node 中运行。

浏览器式打包验证结果：

- 不加 polyfill 时，打包失败，因为 `riichi/yaku.js` 引用了 Node 内置 `assert`。
- 安装 `assert` polyfill 后可以打包并运行，bundle 约 222 KB。
- 尝试用空 `assert` shim 打包后 bundle 约 46 KB，但算点结果出现差异，不建议直接使用未经验证的空 shim。

后续必须在正式微信小程序项目骨架中验证：

- 小程序 npm 构建是否能处理 CommonJS。
- 是否需要 `assert` polyfill。
- 加入 polyfill 后包体积是否可接受。
- 运行结果是否与 Node 测试一致。

## 风险

- 包最近发布时间较早，维护活跃度不足。
- 输出信息偏面向文本展示，结构化程度不完全满足项目需求。
- 不输出符数明细。
- 宝牌输入不是指示牌，需要 adapter 转换。
- 小程序环境需要额外验证 `assert` 兼容。
- 部分规则配置可能无法直接表达项目默认规则。

## 当前建议

继续将 `riichi` 作为第一候选库，但不要直接进入 UI 大规模开发。

下一步建议：

1. 搭建原生微信小程序 + TypeScript 项目骨架。
2. 同时提供浏览器版和微信小程序版两个入口，复用同一套共享验证样例。
3. 在项目中接入 `riichi` 和必要 polyfill。
4. 建立 `scoring adapter` 的最小测试。
5. 用项目规则样例验证 Node、浏览器构建环境和小程序运行环境输出一致。
6. 如果兼容性或规则覆盖失败，再评估换库或补充自研算点逻辑。
