# UI 整体优化设计草案

本文档用于沉淀下一阶段微信小程序 UI 优化方向。目标是在不改变“纯前端手动算点”核心定位的前提下，把当前长表单式页面改造成更适合线下牌桌使用的三段式工作台。

## 设计目标

- 第一屏能看清当前局况、四家点数和主要操作入口。
- 录入动作集中在下方，减少上下滚动。
- 牌面输入面板复用，避免手牌、鸣牌、宝牌各自维护一套 UI。
- 结算前尽量让用户看到“本局发生了什么”，而不是只看到一堆字段。
- 为图标牌、快速补齐和历史记录留下结构空间。
- 将流局作为本轮 UI 优化的一等输入事件纳入设计，包含听牌状态、荒牌罚符和连庄判断。

## 总体可行性评估

整体方案可行，建议拆成两个层次推进：

| 模块 | 可行性 | 说明 |
| --- | --- | --- |
| 上中下三段式布局 | 高 | 主要是页面结构和样式调整，不影响算点核心逻辑 |
| 上方场况区 | 高 | 当前已有局风、局数、本场、供托等状态，可直接迁移 |
| 中间虚拟牌桌 | 高 | 当前已有四家点数和点差数据，UI 需要重新组织 |
| 点击玩家切换立直状态 | 中 | 当前只记录供托数量，不记录每家立直状态，需要新增 per-player 状态 |
| 放铳/自摸输入面板 | 高 | 当前已支持荣和、自摸、和牌者、放铳者 |
| 流局输入面板 | 中到高 | 纳入本轮范围；需要新增四家听牌状态、荒牌罚符和连庄判断 |
| 场面番型输入面板 | 高 | 当前已有和牌条件，改成弹层选择即可 |
| 宝牌/手牌/鸣牌统一牌面板 | 高 | 可复用同一个牌选择组件，但不同输入区需要不同校验规则 |
| 牌图标化 | 中 | 需要设计或引入牌图资源，并处理尺寸、清晰度和包体积 |
| 快速补齐顺子 | 中 | 适合作为后续增强，需要先稳定基础输入体验 |

核心判断：这个方案值得做，并且应该作为独立 UI change 推进。流局虽然会引入结算规则扩展，但它与“本局事件输入面板”强相关，适合纳入这次 UI 工作台改造；复杂历史重算、终局精算和排名分仍应留在后续 change。

## 信息架构

页面分为三个主区域：

```text
------------------------------------------------+
| 上方：场况区                                  |
| 东一局 / 0本场 / 0供托      记录 回退 重置     |
+------------------------------------------------+
| 中间：牌桌区                                  |
|                 北家 25000                    |
|                                                |
|   西家 25000        桌心        东家 25000     |
|                                                |
|                 南家 25000                    |
+------------------------------------------------+
| 下方：结算区                                  |
| 和牌/流局 | 场面番型 | 宝牌 | 手牌 | 鸣牌     |
| [当前选择摘要]                                |
| [确定结算]                                    |
+------------------------------------------------+
```

### 区域职责

- 场况区：展示当前整局状态，承载全局操作。
- 牌桌区：展示四家相对方位、点数、点差和立直状态。
- 结算区：承载本局事件、条件、牌面和结算确认。

## 上方区域：场况区

### 展示内容

场况区建议保持一行主信息和一行操作：

```text
东一局  0本场  0供托
记录    回退结算    重置复位
```

### 功能按钮

| 功能 | 行为 |
| --- | --- |
| 查看记录 | 打开历史结算记录面板，第一版可只展示最近记录列表 |
| 回退结算 | 回到上一局输入快照或最近一局结果，需二次确认 |
| 重置复位 | 清空当前未结算输入，或重置整场点数，必须弹确认框 |

### 设计建议

- 场况区建议固定在顶部或随页面保持高优先级。
- “重置复位”是高风险操作，按钮视觉应弱于“确定结算”，并必须确认。
- “场供”建议统一命名为“供托”，避免术语不一致。

## 中间区域：牌桌区

### 展示内容

每个玩家区域建议展示：

- 方位：东、南、西、北。
- 当前点数。
- 点差摘要。
- 立直状态。

示例：

```text
        北家
       25000
       -1200

西家 24800       东家 26200
-1400            当前最高

        南家
       25000
       -1200
```

### 点差展示策略

四家之间完整两两点差会非常拥挤，建议第一版采用以下策略之一：

| 策略 | 推荐度 | 说明 |
| --- | --- | --- |
| 与当前最高分差 | 高 | 最容易扫读，适合牌桌总览 |
| 与选中玩家的差 | 高 | 用户点击某家后展示该家与其他家的差 |
| 两两点差全部展示 | 低 | 信息量太大，不适合主牌桌视图 |

建议：默认展示“与当前最高分差”；点击玩家后，在底部或弹层展示该玩家与其他三家的点差。

### 立直状态切换

点击玩家可以切换立直状态，建议采用三态或两态：

| 状态 | 说明 |
| --- | --- |
| 未立直 | 默认 |
| 已立直 | 当前桌面供托应 +1，玩家点数是否扣除需要规则决定 |
| 已宣告但未扣点 | 可选，不建议第一版引入 |

建议第一版采用两态，并明确内部规则：

- 如果用户切换某家为已立直，系统自动增加 1 根供托。
- 是否立即从该家点数中扣 1000，需要在设计阶段定死。
- 为避免混乱，建议第一版采用“供托池记录的是桌面已扣出的立直棒”，切换立直时同步从玩家点数扣 1000。

这会比现在只输入供托数量更真实，但需要新增每家立直状态。

## 下方区域：结算区

结算区不建议一次性展开所有输入，而是采用“摘要行 + 输入面板”的模式。

```text
本局事件     荣和：西家 -> 南家
场面番型     立直 / 一发
宝牌         4p, 1z
手牌         13 张
鸣牌         0 组

[确定结算]
```

点击任一输入区域，弹出对应输入面板；确认后关闭面板，摘要区域只展示选择结果。

## 子输入区域 1：本局事件

### 支持类型

| 类型 | 输入内容 | 可行性 |
| --- | --- | --- |
| 放铳 | 放铳者、和牌者 | 当前已支持 |
| 自摸 | 和牌者 | 当前已支持 |
| 流局 | 四家听牌状态、荒牌罚符、是否连庄 | 本轮需要新增结算逻辑 |

### 关于流局的修正建议

流局纳入本轮 UI 优化范围。你提到“流局可以选择庄家是否听牌”，这对是否连庄很重要，但不足以计算流局罚符。四麻荒牌流局通常需要知道四家哪些人听牌：

- 1 人听牌：未听 3 家各付 1000，听牌者收 3000。
- 2 人听牌：未听 2 家各付 1500，听牌 2 家各收 1500。
- 3 人听牌：未听 1 家付 3000，听牌 3 家各收 1000。
- 4 人听牌或 0 人听牌：通常无罚符收支。

因此，流局面板建议是：

```text
流局
[ ] 东家听牌
[ ] 南家听牌
[ ] 西家听牌
[ ] 北家听牌

庄家听牌时连庄：自动判断
```

### 流局结算规则

本轮建议支持标准荒牌流局，不处理途中流局、四风连打、四杠散了、九种九牌、四家立直等特殊流局。

荒牌罚符按 3000 点总额结算：

| 听牌人数 | 点数变化 |
| --- | --- |
| 0 人听牌 | 无收支 |
| 1 人听牌 | 听牌者 +3000，三名未听者各 -1000 |
| 2 人听牌 | 两名听牌者各 +1500，两名未听者各 -1500 |
| 3 人听牌 | 三名听牌者各 +1000，未听者 -3000 |
| 4 人听牌 | 无收支 |

连庄判断建议：

- 亲家听牌：连庄。
- 亲家未听：轮庄。

本场处理建议：

- 荒牌流局后下一局本场 +1。
- 当前 MVP 如果还没有自动推进局数，可以先在结果中展示“下一局本场 +1”和“连庄/轮庄建议”，不强制自动修改局数。

供托处理建议：

- 流局时供托留在桌面，不分配给任何人。
- 已立直玩家的立直棒仍留在供托池，下一次和牌时归和牌者。

结果展示建议：

```text
荒牌流局
听牌：东家、南家
东家 +1500
南家 +1500
西家 -1500
北家 -1500
亲家听牌，连庄；下一局 1 本场
供托继续保留：2 根
```

## 子输入区域 2：场面番型

### 范围

场面番型包括：

- 立直。
- 双立直。
- 一发。
- 抢杠。
- 海底。
- 河底。
- 岭上。
- 天和。
- 地和。
- 里宝牌启用。

### UI 形式

你提到使用 radio，这里建议区分两类：

| 类型 | 控件 | 原因 |
| --- | --- | --- |
| 互斥条件 | radio | 例如无/海底/河底/岭上/抢杠，在多数情况下不应同时存在 |
| 可叠加条件 | checkbox 或 switch | 立直、一发、里宝牌启用等可以与其他条件组合 |

推荐面板结构：

```text
立直状态
( ) 无
( ) 立直
( ) 双立直

偶发条件
[ ] 一发
[ ] 抢杠
[ ] 岭上
[ ] 海底
[ ] 河底

役满条件
[ ] 天和
[ ] 地和

[确定]
```

确认后摘要展示：

```text
立直 / 一发 / 里宝牌
```

## 子输入区域 3：宝牌指示牌

### 展示

预留 8 个框和一个图标入口：

```text
宝牌  [ ] [ ] [ ] [ ] [ ] [ ] [ ] [ ]  +
```

8 个框可以覆盖：

- 普通宝牌指示牌。
- 杠宝牌指示牌。
- 里宝牌指示牌。

但需要在数据模型中区分类型，否则算点时无法判断里宝牌是否仅立直后生效。建议有两种方案：

| 方案 | 说明 | 推荐 |
| --- | --- | --- |
| 一个 8 格列表 + 每格类型标记 | 每张指示牌可标记为宝牌/杠宝/里宝 | 中 |
| 三段列表，但共用同一弹层 | 宝牌、杠宝、里宝各自保留区域 | 高 |

建议：第一版仍保留三段数据，但 UI 可以折叠成一个“宝牌”区域，内部用小标签区分“宝牌 / 杠宝 / 里宝”。

### 输入面板

面板分为四行：

```text
万：1 2 3 4 5 6 7 8 9 0
索：1 2 3 4 5 6 7 8 9 0
筒：1 2 3 4 5 6 7 8 9 0
字：东 南 西 北 白 发 中
```

注意：项目内部编码目前使用 `m/p/s`，不是 `w/s/m`。UI 可以显示“万/索/筒”，内部仍应保存为 `m/s/p`。

### 赤五处理

`0` 代表赤五，这对手牌和鸣牌有意义；对宝牌指示牌需要谨慎：

- 如果用户选择 `0m` 作为宝牌指示牌，算点时可以按普通 `5m` 指示 `6m` 处理。
- UI 上可以允许选择，但保存前应归一化为普通 5，避免误以为“赤五指示牌会额外给赤宝番”。

## 子输入区域 4：手牌

### 展示

预留 13 个框和一个图标入口：

```text
手牌  [ ][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ]  +
```

点击任一框打开同一个牌输入面板。选择后：

- 填入当前框。
- 自动移动到下一个空框。
- 到第 13 格后保持在最后一格或关闭面板，可在交互测试后决定。

### 后续快速填入

快速填入可以作为后续增强，不进入第一版 UI 优化的必做范围。可能规则：

- 输入 `4s 5s` 后提示“一键补 6s”。
- 输入对子后提示“补刻子”。
- 输入 `123` 顺子时自动推进到下一个空位。

这类能力会明显提升效率，但也容易误填，应在基础面板稳定后再做。

## 子输入区域 5：鸣牌

### 展示

预留 16 个框和一个图标入口：

```text
鸣牌  [ ][ ][ ][ ] [ ][ ][ ][ ] [ ][ ][ ][ ] [ ][ ][ ][ ]  +
```

16 格可以覆盖最多 4 组副露/杠，每组 4 格。

### 必要补充

鸣牌不能只输入牌，还需要保存面子类型：

- 吃。
- 碰。
- 明杠。
- 暗杠。
- 加杠。

建议 UI 表达为“每 4 格一组”，每组上方或左侧有一个类型选择：

```text
鸣牌
吃   [3s][4s][5s][ ]
碰   [东][东][东][ ]
暗杠 [5m][5m][5m][5m]
```

如果只展示 16 个连续格，用户会不清楚哪些牌属于同一组副露，也会影响后续符数和门清判断。

## 控制按钮与确认框

结算区底部提供主要按钮：

```text
[确定结算]
```

点击后弹出确认框，建议内容包含摘要：

```text
确认结算？

东一局 0本场 0供托
荣和：西家放铳，南家和牌
手牌 13 张，鸣牌 0 组，宝牌 1 张

[返回修改] [确认结算]
```

确认框的价值不是防误触而已，它还能让用户在最终算点前快速复核本局关键输入。

## 状态模型建议

为了支撑这套 UI，页面状态建议从“长表单字段”调整为“当前局快照 + 当前编辑面板”。

```ts
type EditingPanel =
  | "none"
  | "round-event"
  | "scene-yaku"
  | "dora"
  | "hand"
  | "meld";

type RoundEvent =
  | { type: "ron"; winner: Seat; discarder: Seat }
  | { type: "tsumo"; winner: Seat }
  | { type: "draw"; tenpaiSeats: Seat[] };
```

流局进入本 change，需要新增 `draw` 结算逻辑。`draw` 事件不进入 `riichi` 算点 adapter，而是直接进入本局结算模块。

## 实施建议

### 第一阶段：布局重构

- 改成上中下三段式结构。
- 场况区展示局风、局数、本场、供托和全局按钮。
- 中间区域重做虚拟牌桌。
- 下方区域改成摘要行和弹层入口。
- 本局事件入口包含放铳、自摸、流局三种类型。

### 第二阶段：弹层输入

- 实现本局事件面板：放铳、自摸、流局。
- 流局面板支持四家听牌状态。
- 实现场面番型面板。
- 实现复用牌输入面板。
- 手牌、宝牌、鸣牌都接入同一个面板。

### 第三阶段：牌桌交互

- 点击玩家切换立直状态。
- 展示每家点数、与最高分差、选中玩家点差。
- 确定立直棒与点数扣减规则。
- 流局结果展示荒牌罚符、连庄/轮庄和本场变化建议。

### 第四阶段：效率增强

- 增加顺子/刻子快速补齐。
- 替换文字牌为 icon 图标。

## 主要风险

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 流局扩大规则范围 | 会触及结算模型，不只是 UI | 纳入本 change，但严格限定为荒牌流局和四家听牌状态 |
| 立直状态与供托重复输入 | 容易导致供托数量不一致 | 确定一个唯一来源，建议由玩家立直状态推导供托 |
| 鸣牌 16 格缺少组信息 | 会影响符数、门清、副露判断 | 每 4 格为一组，并必须选择面子类型 |
| 宝牌指示牌赤五语义不清 | 用户可能误解指示牌和赤宝牌 | 指示牌选择赤五时按普通五处理，并在 UI 文案中弱提示 |
| 三段式在小屏仍可能拥挤 | 牌桌和下方操作都想占空间 | 中间牌桌保持紧凑，下方输入采用弹层 |

## 推荐结论

推荐采用这个三段式方案作为下一阶段 UI 优化方向，但建议将范围控制为：

- 必做：三段式布局、虚拟牌桌、弹层输入、复用牌面板、确认结算弹窗、荒牌流局结算。
- 可选：玩家立直状态切换。
- 后置：途中流局、快速补齐、牌 icon 全量替换。

这样既能显著改善当前页面过长的问题，也能补齐线下牌桌非常常见的荒牌流局场景；同时通过限定流局范围，避免 UI 优化 change 膨胀成完整赛事规则引擎。

## 实现落地记录

`optimize-scoring-workbench-ui` change 的实现采用了以下落地方案：

- 主页面已改为场况区、牌桌区、结算区三段式工作台。
- 本局事件、场面番型、手牌、宝牌、鸣牌和记录均通过底部弹层编辑。
- 标准荒牌流局已经进入结算模型，支持四家听牌状态、荒牌罚符、连庄/轮庄、本场 +1 和供托保留。
