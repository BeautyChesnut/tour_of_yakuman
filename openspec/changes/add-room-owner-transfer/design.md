## Context

在线房间采用单一房主写入模型：房主可以修改算点状态、洗座和确认结算，其他成员只读。当前只有房主退出房间时才会随机选择继任者，无法主动指定交接对象。小程序优先调用微信云托管 HTTP 服务，同时保留同名云函数作为备用通道。

## Goals / Non-Goals

**Goals:**

- 在不改变单写模型的前提下允许房主主动转让。
- 保证目标必须是房间内已入座成员，并由服务端完成最终鉴权。
- 转让成功后立即刷新发起端角色和房间成员展示。
- 保持云托管与云函数备用通道行为一致。

**Non-Goals:**

- 不开放普通成员共同编辑。
- 不实现踢人、管理员、多房主或房主转让历史。
- 不允许转让给未入座、已离开或仅凭 openId 指定的用户。

## Decisions

1. 新增独立 `transferRoomOwner` 操作，而不是复用普通房间更新。房主身份属于权限边界，独立接口便于校验、审计日志和测试，也避免客户端通过通用更新修改 `ownerOpenId`。
2. 请求只携带 `roomId` 与 `targetOpenId`。发起者身份继续由可信微信上下文获取，服务端依次校验房间状态、当前房主、非本人目标和目标在 `seatMap` 中。
3. 接口返回更新后的 `room` 与当前 `state`。原房主收到结果后立即切换为 `room-viewer`；新房主在下一次刷新房间状态时依据 `ownerOpenId` 自动切换为 `room-host`。
4. 转让入口放在成员面板的已入座成员行中。只有当前房主查看其他成员时显示“转让房主”，点击后使用系统确认框二次确认。
5. 不修改计分状态版本。转让只改变房间元数据，现有状态继续有效；写操作仍在服务端逐次校验最新房主身份。

## Risks / Trade-offs

- [两端刷新时序不同，新房主可能短暂仍显示只读] → 房间刷新结果统一根据最新 `ownerOpenId` 重算本地角色，并在转让成功后提示新房主刷新。
- [旧房主转让前发出的写请求与转让并发] → 每个写接口继续在持久化前读取并校验当前房主；不引入多人编辑或客户端乐观授权。
- [云托管和云函数实现漂移] → 使用相同输入输出和错误文案，并为云函数和前端服务映射补充测试。

## Migration Plan

先发布包含新云函数/云托管接口的服务端，再上传调用新接口的小程序。旧客户端不受新增接口影响；回滚小程序后服务端保留未调用接口也不会改变既有房间。
