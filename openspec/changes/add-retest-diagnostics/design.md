## Context

服务端已有 `requestId` 和数据库操作日志，但请求响应未把诊断信息返回客户端；小程序错误主要以字符串处理，容易把不同错误归为同一提示。项目不希望引入第三方监控或增加用户反馈步骤。

## Goals / Non-Goals

**Goals:**

- 自动关联小程序错误与云托管日志。
- 自动识别小程序和服务 API 不兼容。
- 对不会造成重复业务写入的请求自动重试一次。
- 本地自动保存并恢复未完成算点草稿。
- 诊断数据保持最小化并使用现有云托管日志。

**Non-Goals:**

- 不做反馈表单、诊断页面或管理后台。
- 不接入第三方监控 SDK。
- 不上传完整 openid、昵称、头像、房间码、手牌或点数状态。
- 不自动重试创建房间、转让房主、状态写入和确认结算。

## Decisions

1. 服务响应增加 `_service` 元数据，错误响应增加 `code`、`requestId` 和 `retryable`，业务主体保持不变。
2. 客户端诊断事件通过独立接口写入结构化控制台日志，不落新数据库表；事件字段采用白名单。
3. 仅 `login`、`joinRoom` 及服务信息请求允许一次网络级重试；业务错误不重试。
4. 本地草稿使用小程序本地存储，保存共享算点输入和玩法，不上传云端；完成结算或重置时覆盖为最新干净状态。
5. 房间版本冲突由页面刷新最新房间状态，避免继续覆盖；刷新失败才展示错误。

## Risks / Trade-offs

- [诊断上报本身失败] → 静默忽略，不影响核心算点和在线房间。
- [自动重试造成重复写入] → 只允许幂等或安全请求重试。
- [旧草稿与新代码结构不兼容] → 草稿带 schema 版本，解析失败时静默丢弃。
- [日志量增加] → 仅上报失败和未处理异常，不上报高频输入过程。
