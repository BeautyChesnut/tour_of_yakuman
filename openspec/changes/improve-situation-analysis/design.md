## Context

局势分析目前由纯 TypeScript 模块根据四家点数枚举合法打点，并在在线房间内展示升位和跌四风险。入口同时受在线模式、VIP 权限和四人满员限制；新用户默认是免费用户，项目又没有会员开通流程，因此能力难以触达。分析模块还自行模拟本场、供托和点数转移，与正式 `settlement` 模块形成两套实现。

本变更跨越会员权限、算点工作台、局势分析页面和结算领域模块，但不改变云托管接口或房间数据结构。

## Goals / Non-Goals

**Goals:**

- 让四麻局势分析在本地模式和在线模式中均可使用，便于真实验收。
- 在线房间未满员时仍可依据已有四家点数进行推演。
- 为本地模式提供明确的分析视角，并允许在详情页切换东南西北。
- 让局势分析和正式结算共享本场、供托、支付合并和点数变化逻辑。
- 用交叉测试确认常见点数档和边界场景不会发生规则漂移。

**Non-Goals:**

- 不实现三麻局势分析。
- 不接入大模型、牌河识别、向听计算或攻防概率。
- 不实现会员购买、支付、后台授权或订阅管理。
- 不修改在线房间协议、数据库结构或正式算点结果。

## Decisions

### 测试阶段不以会员权限阻挡局势分析

`canUseSituationAnalysis` 在当前阶段对免费和 VIP 用户均为真，保留字段以便未来重新制定会员策略。相比直接删除会员字段，这种方式不会影响现有用户数据和主题权限，也便于以后独立调整。

替代方案是先实现会员购买或手工配置 VIP；但这会把支付和运营后台引入当前变更，无法解决近期验收需求。

### 四麻按模式选择默认视角，并在详情页允许切换

在线房间默认使用当前登录用户的座位；本地四麻默认使用当前庄家座位。详情页提供东南西北分段选择，切换后立即重新计算全部目标和风险场景。这样不需要把临时视角写入房间共享状态，也不需要新增持久化字段。

### 未满员在线房间仍可分析

点数推演只依赖四家点数和局况，不依赖四个微信用户记录。空座位使用现有本地玩家名作为展示兜底；当前用户已在房间中即可获得自己的默认视角。

### 结算模块提供通用手牌支付结算入口

在 `settlement` 模块新增接收结构化手牌支付的结算函数，统一追加本场、供托并计算点数变化。现有 `applyRoundSettlement` 改为委托该函数；局势分析只负责生成候选手牌支付，不再自行维护本场、供托和总点数转移公式。

候选符番和合法点数枚举仍保留在局势分析模块，因为它表达的是“达到目标所需的最小合法打点”，不是对具体手牌进行正式算点。

### 保持“点数推演”产品定位

页面继续使用“局势分析”和“点数推演”，并明确提示结果不包含手牌、巡目和牌河判断。当前阶段不出现“AI 推荐”或类似可能夸大能力的文案。

## Risks / Trade-offs

- [免费开放会偏离未来会员规划] → 将其定义为测试阶段策略，并保留独立权限字段，未来可通过新变更恢复限制。
- [本地模式默认庄家视角不一定是用户本人] → 详情页始终显示分析视角选择，用户可一键切换。
- [共享结算函数调整可能影响正式结算] → 保持 `applyRoundSettlement` 对外签名不变，并用现有全量结算测试加专项交叉测试保护。
- [空座位名称可能让用户误以为真人已加入] → 仅在分析结果中使用玩家名称兜底，不改变牌桌的“等待加入”状态。
- [合法点数枚举仍可能和第三方库边界不一致] → 为常见符番、满贯以上、庄家/子家、荣和/自摸建立表驱动交叉测试。

## Migration Plan

1. 先增加共享结算函数并保持现有入口委托，运行原有结算测试。
2. 切换局势分析到共享结算函数，补充交叉测试。
3. 放开权限和模式限制，增加本地默认视角及详情页切换。
4. 更新文档并在微信开发者工具中分别验收本地四麻、未满员在线房间和完整在线房间。

如出现回归，可恢复旧入口条件和旧局势分析模拟函数；本变更没有数据库迁移。

## Open Questions

- 会员体系正式上线时，局势分析是否继续免费、按次数限制或作为 VIP 权益，需要独立产品决策。
- 三麻的目标点数和自摸损失规则需要单独 OpenSpec，不在本次设计中预设。
