## Context

当前项目是一款纯前端微信小程序，算点、结算、点数推进和 UI 状态都在本地页面内完成。2.0 希望让四名真实微信用户进入同一个房间，共享当前牌桌、点数和结算记录，并保持现有牌桌布局与手动录入效率。

这会引入两个新边界：

- 用户身份边界：从无账号变为微信登录用户。
- 房间状态边界：从本地页面状态变为可同步、可持久化的房间共享状态。

当前算点引擎仍应保持纯 TypeScript，不直接依赖微信 UI 或后端服务。房间功能应围绕现有领域数据结构包装，而不是把算点逻辑迁移进页面组件或云函数业务代码中。

## Goals / Non-Goals

**Goals:**

- 支持微信用户登录，并以微信身份加入房间。
- 支持房主创建一个四人房间，其他玩家通过房间码或邀请入口加入。
- 支持东、南、西、北四个座位绑定真实微信用户。
- 房间内保持当前牌桌布局，展示四家点数、局况、摘要和结算结果。
- 仅房主可以编辑局况、牌面、鸣牌、宝牌、点数和确认结算。
- 非房主成员只能查看房间状态，不能修改共享算点数据。
- 房主确认结算后，房间成员能看到同步后的点数和结算记录。

**Non-Goals:**

- 不支持多人同时编辑。
- 不支持旁观者、聊天、语音、联机打牌或实时出牌。
- 不支持房主转让、踢人、复杂断线重连策略。
- 不支持任意历史局编辑并重算后续点数。
- 不要求第一版在线房间离线可用；单机模式仍保留为无网络兜底。
- 不在本变更中实现拍照识别、账号体系扩展或自定义地方规则。

## Decisions

### 1. 后台优先采用微信云开发

优先使用微信云开发云函数和云数据库承载登录、房间和状态持久化。

理由：

- 与微信小程序登录和 openid 集成成本最低。
- 避免第一版 2.0 引入独立服务器部署、证书、域名备案和自建鉴权。
- 云数据库可支持房间状态持久化和基础实时监听，适合房主单写、成员只读的轻协作场景。

备选方案：

- 自建 Node.js 后端：更自由，但部署和运维成本更高。
- 继续纯前端：无法满足真实微信用户登录和多人房间同步。

### 2. 保留单机模式，新增在线房间模式

应用入口新增在线房间入口，但保留当前单机算点入口。在线房间模式复用现有算点工作台 UI 和算点引擎。

理由：

- 单机模式是当前已发布能力，不应因 2.0 引入网络依赖而退化。
- 在线房间第一版可能受网络和云服务影响，单机模式可作为兜底。
- 复用 UI 能降低迁移风险，并保持用户熟悉的操作方式。

### 3. 区分本地 UI 状态与房间共享状态

页面状态拆为两类：

- 本地 UI 状态：当前打开的弹层、当前选中的牌格、临时错误提示、确认弹窗状态。
- 房间共享状态：局况、四家点数、座位成员、手牌/和牌张/鸣牌/宝牌、场面番型、结算记录。

理由：

- 本地 UI 状态不应同步给其他玩家。
- 房间共享状态需要持久化和同步。
- 这个拆分可以避免只读成员误触发编辑，也能降低状态覆盖冲突。

### 4. 房主单写，后端强制校验权限

房主是房间共享状态唯一写入者。小程序端根据角色隐藏或禁用编辑入口，云函数也必须校验 `openid === room.ownerOpenId`。

理由：

- UI 禁用不能作为安全边界。
- 房主单写避免多人编辑冲突，不需要 CRDT、锁或复杂合并策略。
- 线下麻将算点通常由一人负责录入，符合实际使用场景。

### 5. 房间共享状态使用版本号防止旧状态覆盖

`RoomState` 包含递增 `version` 和 `updatedAt`。房主提交更新时带上当前版本，后端发现版本过旧时拒绝写入并返回最新状态。

理由：

- 避免房主设备上的过期页面覆盖较新的结算结果。
- 便于后续做乐观更新和错误提示。
- 成员只读场景不需要复杂冲突解决。

### 6. 算点可先在房主端计算，后端保存结构化结果

第一版在线房间中，房主端继续调用现有 TypeScript 算点引擎，确认后将输入快照、算点结果和结算后点数写入房间状态。后续可增加云函数复算校验。

理由：

- 当前算点引擎已经前端可运行，迁移成本低。
- MVP 优先完成房间共享体验。
- 后端复算会涉及打包共享算法到云函数，可作为增强项。

## Risks / Trade-offs

- [风险] 微信云开发配置、权限和环境变量增加发布复杂度。
  [缓解] 新增 `docs/` 文档记录云环境、集合、云函数和上传流程；单机模式保留。

- [风险] 当前 `pages/scoring/index.ts` 状态较重，直接塞入房间逻辑会变难维护。
  [缓解] 先抽出房间服务、共享状态 adapter 和只读权限判断，再逐步接入页面。

- [风险] 数据库实时监听在弱网下可能延迟。
  [缓解] 第一版允许显示同步状态和手动刷新；房主提交后以服务端返回为准。

- [风险] 用户昵称头像授权策略可能受微信隐私规范影响。
  [缓解] 登录只依赖 openid；展示名和头像使用用户主动授权或本地填写的昵称，不把昵称作为身份凭据。

- [风险] 非房主只读但仍可能看到未完成输入。
  [缓解] 这是房间共享算点桌的预期行为；只同步结构化输入，不同步房主当前焦点、弹层和临时错误。

## Migration Plan

1. 保留现有单机算点入口和本地存储行为。
2. 新增云开发初始化、登录服务和用户身份缓存。
3. 新增在线房间入口、创建房间和加入房间页面。
4. 新增房间共享状态模型，并实现房主写入和成员读取。
5. 将现有算点工作台接入 `mode: "local" | "room-host" | "room-viewer"`。
6. 接入房主确认结算后的房间状态持久化。
7. 更新发布、隐私和路线图文档。

回滚策略：

- 若在线房间功能异常，可以隐藏在线入口并保留单机算点能力。
- 云端数据结构变更应向后兼容，避免影响已经上传的单机版本。

## Open Questions

- 房间加入方式采用房间码、二维码还是微信分享卡片优先？
- 座位绑定由房主分配，还是玩家加入时自选空座？
- 用户展示名使用微信授权资料、本地昵称，还是房间内临时昵称？
- 第一版是否需要云函数复算防止房主端结果被篡改？
- 房间状态保留多久，是否需要自动关闭或清理过期房间？
