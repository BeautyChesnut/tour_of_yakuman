## Context

项目当前只有 OpenSpec、路线图、规则文档和项目约束，还没有应用代码。第一版目标是微信小程序上的纯前端手动录入算点 MVP：用户手动输入牌面和局况，系统在前端完成番符、役种、支付、结算后点数和点差计算。

关键约束：

- 文档和用户展示文案尽量使用中文，文本文件使用 UTF-8 编码。
- 第一版不依赖后台服务，不做登录，不做拍照识别。
- 算点引擎必须独立于 UI，方便测试和后续复用。
- 规则细节以 `docs/riichi-scoring-rules.md` 为准。

## Goals / Non-Goals

**Goals:**

- 建立微信小程序的前端项目骨架和 TypeScript 工程基础。
- 提供浏览器版和微信小程序版两个运行入口，复用同一套算点/adapter 逻辑。
- 实现手动牌面录入、局况设置、和牌条件选择、结果展示的 MVP 流程。
- 实现可测试的领域模块：牌工具、算点、局况、结算。
- 支持最近一局从结果页返回修改，并重新结算覆盖当前结果。
- 支持四人立直麻将常见单一和牌者结算。

**Non-Goals:**

- 后台服务、账号体系和云端同步。
- 拍照识别和图片上传。
- 三人麻将。
- 多人同时和牌、包牌、流局罚符、途中流局。
- 终局马点、返点和排名分。
- 历史任意局修改后重算后续点数。

## Decisions

### 决策 1：优先使用成熟第三方日麻库，并通过 adapter 隔离

番符、役种和基础支付计算优先使用成熟第三方日麻库。项目内部仍然定义稳定的 `HandInput`、`RoundInput` 和 `ScoringResult`，通过 `scoring adapter` 将项目模型转换为第三方库输入，再将第三方库结果转换回项目结果。

理由：

- 立直麻将番符边界多，自研完整算点引擎容易漏规则。
- 成熟第三方库可以更快验证 MVP，并降低第一版规则错误风险。
- adapter 可以避免 UI 和产品数据结构被某个库绑定死。
- 后续如果第三方库不满足需求，可以替换 adapter 或补充自研逻辑。

备选方案：

- 完全自研算点引擎。该方案长期可控，但第一版工作量大，且需要大量规则测试支撑。
- 将第三方库数据结构直接暴露给 UI。该方案接入更快，但会增加后续替换成本。

### 决策 2：项目内部定义稳定输入输出模型

项目内部定义 `Tile`、`Meld`、`RoundInput`、`HandInput`、`ScoringResult`、`SettlementRecord` 等模型。UI 和算点模块都围绕这些模型交互。

理由：

- 避免 UI 状态直接泄漏到算点逻辑。
- 后续如果引入第三方日麻库，可以通过 adapter 转换，不改变 UI 和结算模块。
- 文档、测试和实现可以使用同一套术语。

备选方案：

- 直接采用第三方库的数据结构。该方案能减少转换代码，但会把产品输入流程绑定到外部库细节。

### 决策 3：第一版只支持最近一局返回修改

结算结果页支持返回修改最近一局输入，重新确认后覆盖当前结果。历史任意局修改及后续点数重算后置。

理由：

- 满足“每一局结算支持后退并重新修改结算”的核心使用场景。
- 避免第一版过早引入复杂历史重算、局数推进和整场牌谱状态管理。

备选方案：

- 一开始支持任意历史局修改。该方案更完整，但需要处理后续所有局的连锁重算，明显扩大 MVP 范围。

### 决策 4：手动输入优先，拍照识别作为后续增强

第一版所有手牌、副露、杠牌、宝牌、杠宝牌、里宝牌和局况都由用户手动输入或指定。

理由：

- 手动录入可以先验证算点闭环和 UI 体验。
- 拍照识别存在模型、图片质量、牌字体、遮挡和隐私问题，不适合作为第一版核心路径。

备选方案：

- 第一版加入拍照识别。该方案更吸引人，但会显著增加不确定性，并拖慢算点工具本身的验证。

### 决策 5：输入组件采用“上方格子 + 下方牌盘”的交互

牌面录入参考停车费缴费应用的车牌号输入方式：用户先选中上方格子，再从下方牌盘选择牌。

理由：

- 移动端上比普通下拉框或键盘输入更直观。
- 容易支持替换、清空、牌数异常提示和分组切换。
- 符合用户“填牌”的心智模型。

备选方案：

- 使用文本输入或麻将牌缩写输入。该方案对熟练用户更快，但对目标用户更容易出错。

### 决策 6：同时提供浏览器版和微信小程序版

项目 SHALL 提供浏览器版和微信小程序版两个打包目标。浏览器版用于快速验证、演示和调试；微信小程序版用于最终目标平台。两个版本复用同一套共享领域逻辑和兼容验证样例。

理由：

- 浏览器版构建和访问成本低，适合快速验证 `riichi` adapter、输入流程和结果展示。
- 微信小程序版是最终产品形态，必须保留真实平台验证。
- 双目标可以更早暴露打包兼容问题，同时避免算点逻辑在两个端重复实现。

备选方案：

- 只做微信小程序版。该方案目标聚焦，但调试和演示成本更高。
- 先做浏览器版再迁移小程序。该方案开发快，但容易引入小程序运行环境不兼容的设计。

## Risks / Trade-offs

- [Risk] 第三方日麻库的规则默认值可能与项目规则不一致。→ Mitigation：在 adapter 层显式配置规则，并用项目测试样例校验输出。
- [Risk] 第三方库可能不完全支持微信小程序运行环境。→ Mitigation：优先选择 TypeScript/JavaScript 纯运行时库；接入前做小程序构建和运行验证。
- [Risk] 第三方库可能缺少某些结果明细或扩展能力。→ Mitigation：在项目层补充结算、点差、展示文案和必要的规则包装；无法覆盖时再补充自研逻辑。
- [Risk] 第一版不支持拍照识别，产品吸引力可能弱于最初愿景。→ Mitigation：明确拍照识别是阶段 4 增强，第一版先把可靠算点和输入体验做扎实。
- [Risk] 牌面输入步骤较多，用户可能觉得繁琐。→ Mitigation：使用格子式输入、牌组切换、常用副露模板和明确错误提示减少操作成本。
- [Risk] 最近一局修改不能覆盖复杂整场纠错。→ Mitigation：在 MVP 中只承诺最近一局回退，历史任意局修改作为体验打磨阶段评估项。
- [Risk] 微信小程序环境与普通 Web 测试工具存在差异。→ Mitigation：领域模块用普通 TypeScript 单元测试验证，UI 交互另行用小程序可用的测试方式覆盖关键路径。

## Migration Plan

这是新项目能力，无现有生产数据迁移。

实施顺序：

1. 创建前端工程骨架和测试基础。
2. 调研并选择第三方日麻库，验证其规则覆盖和微信小程序兼容性。
3. 建立浏览器版和微信小程序版入口，并确认共享逻辑可被两个目标复用。
4. 实现领域数据模型、牌工具、第三方库 adapter 和结算基础。
5. 接入第三方库完成最小算点能力并补充测试。
6. 实现手动输入 UI、局况 UI、条件 UI 和结果页。
7. 联调完整单局结算闭环。

回退策略：

- 若 UI 实现受阻，领域模块和测试可以保留，不影响后续替换 UI 方案。
- 若算点覆盖不足，先限制可结算牌型范围并在 UI 中提示未支持，再逐步扩展。

## 已决策

- 第一版使用原生微信小程序 + TypeScript。
- 第一版同时提供浏览器版和微信小程序版两个打包目标。
- 第一版优先评估并接入第三方日麻库，首选候选为 `riichi`，通过项目内 `scoring adapter` 隔离。
- 切上满贯做成规则配置项，默认关闭。
- 累计役满做成规则配置项，默认开启。
- 多倍役满做成规则配置项，默认开启。
- 双风雀头默认按 4 符处理；双风雀头 2 符规则第一版暂不支持。
- 第一版界面使用中文主文案，并在役种等关键术语处辅助展示日文术语。
- 副露输入优先使用吃、碰、明杠、暗杠、加杠快捷模板，不以逐张自由填格子作为主路径。

## 待验证

- `riichi` 已完成初步 Node 环境验证，结论见 `docs/riichi-library-spike.md`。
- `riichi` 是否能在正式微信小程序 npm 构建和运行环境中正常使用，仍需在项目骨架中验证。
- 浏览器版已可通过 Vite 构建；仍需在后续真实功能页面中持续确认共享逻辑不会产生端侧差异。
- `riichi` 支持累计役满，adapter 已在拿到 `数え役満` 结果后将项目侧牌值和基础点修正为役满。
- 切上满贯和双风雀头 2 符规则第一版暂不支持，后续如有需要再由 adapter 或自研符数模块补齐。
- `riichi` 不输出符数明细；需要决定第一版由项目层补齐符数明细，还是将符数明细后置。
- 如果 `riichi` 无法覆盖某些规则，adapter 层应补齐、标记暂不支持，还是改用其他库。
- 副露快捷模板对赤五相关副露是否足够顺手，是否需要允许用户替换模板中的普通五为赤五。
