## Context

当前微信小程序算点页已经具备纯前端本地算点、手动牌面输入、四家点数维护、最近一局返回修改等 MVP 能力，但页面仍是长表单结构：局况、点数、手牌、和牌张、副露、宝牌、条件和结果被纵向展开。线下牌桌场景里，用户更需要快速扫读当前局况和四家点数，再在底部完成本局事件与牌面补充。

`docs/ui-optimization-design.md` 已沉淀 UI 原型方向：上方场况区、中间牌桌区、下方结算区。后续实现应以微信小程序为主，不再为了浏览器验证牺牲小程序交互结构；共享领域模块仍保留，用于算点、校验、结算和测试。

## Goals / Non-Goals

**Goals:**

- 将算点页从长表单改造成三段式工作台，减少滚动和信息割裂。
- 用底部弹层承载本局事件、场面番型、宝牌、手牌、鸣牌等输入。
- 手牌与和牌张同排展示，和牌张独立高亮，满足平和、听牌形等识别需要。
- 将标准荒牌流局纳入本局事件，支持四家听牌状态、荒牌罚符、连庄/轮庄、本场 +1 和供托保留。
- 保持纯前端本地结算，不增加后台服务。
- 通过领域模块测试覆盖流局结算和输入状态转换。

**Non-Goals:**

- 不支持途中流局、四风连打、四杠散了、九种九牌、四家立直等特殊流局。
- 不实现任意历史局重算，仍只承诺最近一局返回修改。
- 不在本 change 中完成顺子/刻子快速补齐。
- 不强制完成全量麻将牌 icon 替换，只预留组件结构和样式空间。
- 不改动 `riichi` 第三方库选型；荒牌流局不通过 `riichi` 计算。

## Decisions

### Decision: 页面采用“局快照 + 当前编辑面板”的状态模型

页面状态从一组散落表单字段收敛为两个层次：

- 当前局快照：局况、四家点数、本局事件、牌面输入、场面番型、结算记录。
- 当前编辑面板：`none | round-event | scene-yaku | dora | hand | meld | confirm`。

这样每个输入区都可以先在弹层内编辑，确认后只把摘要同步回主界面。相比继续扩展长表单，这个模型更适合小屏和后续图标牌替换。

### Decision: 本局事件升级为 `ron | tsumo | draw`

现有 `WinType` 只有 `ron | tsumo`，适合和牌计算，但不能表达流局。实现时建议新增更上层的 `RoundEvent`：

```ts
type RoundEvent =
  | { type: "ron"; winner: Seat; discarder: Seat }
  | { type: "tsumo"; winner: Seat }
  | { type: "draw"; tenpaiSeats: Seat[] };
```

和牌事件继续构造 `RoundInput` 并进入 `calculateWithRiichi`；流局事件直接进入 settlement 模块，生成荒牌罚符支付、点数变化和下一局提示。

### Decision: 标准荒牌流局由 settlement 模块直接计算

荒牌流局没有役种、番数、符数，也不需要 `riichi` adapter。 settlement 模块应新增独立路径：

- 0 或 4 家听牌：无罚符收支。
- 1 家听牌：听牌者 +3000，三名未听各 -1000。
- 2 家听牌：两名听牌者各 +1500，两名未听各 -1500。
- 3 家听牌：三名听牌者各 +1000，未听者 -3000。
- 亲家听牌：连庄；亲家未听：轮庄。
- 荒牌流局后本场 +1，供托不分配。

该路径应返回结构化结果，方便结果页展示“听牌者、每家变化、连庄/轮庄、本场变化、供托保留”。

### Decision: 手牌与和牌张同排，但数据仍独立

UI 上展示为“13 张手牌 + 1 张和牌张”，和牌张使用分隔、描边或标签突出。数据模型继续保留：

- `concealedTiles: Tile[]`
- `winningTile?: Tile`

这样既符合用户按牌面横向录入的直觉，也避免把和牌张混进手牌导致算点 adapter 难以判断和牌形。

### Decision: 牌选择面板复用，输入区负责校验规则

宝牌、手牌、和牌张、鸣牌都使用统一的牌选择面板，面板只负责展示和选择：

- 万、索、筒、字四行。
- 0 表示赤五。
- 选择后自动推进到下一个空格。

不同区域在保存前执行自己的规则：

- 手牌和鸣牌允许赤五。
- 宝牌指示牌选择赤五时归一化为普通五。
- 鸣牌按组保存，并必须带面子类型。

### Decision: 场面番型面板区分互斥项和可叠加项

“立直/双立直/无”是互斥关系，适合 radio；一发、抢杠、岭上、海底、河底、天和、地和、里宝牌启用等条件需要按规则分组。实现时应避免一个 radio 组覆盖所有场面番型，否则会误伤可叠加条件。

### Decision: 玩家立直状态作为本 change 的可实现项，但必须单一来源

牌桌区可以点击玩家切换立直状态。为避免“手输供托”和“玩家立直状态”产生冲突，实现时应选择单一来源。建议规则：

- 玩家切换为已立直时，该玩家点数立即 -1000。
- 桌面供托 +1。
- 再次取消立直时回滚该 1000 点和供托。

如果实现复杂度过高，可以先保留显式供托输入，但不能同时让两套入口无约束地修改供托。

## Risks / Trade-offs

- 流局让 UI change 触及结算模型 → 严格限定为标准荒牌流局，不处理特殊流局。
- 三段式布局在小屏仍可能拥挤 → 中间牌桌保持紧凑，输入细节全部放到底部弹层。
- 玩家立直状态和供托可能重复修改 → 实现时必须明确一个唯一来源，并在 UI 上隐藏或弱化另一个入口。
- 鸣牌 16 格如果不分组会影响符数和门清判断 → 每 4 格为一组，并要求选择面子类型。
- 宝牌指示牌赤五容易被误解 → 保存前归一化为普通五，必要时在输入面板给出弱提示。
- 全量 icon 牌会影响包体积和清晰度 → 本 change 只预留 icon 化结构，正式素材替换后续单独评估。

## Migration Plan

1. 先补领域测试：标准荒牌流局支付、供托保留、本场 +1、亲家听牌连庄、亲家未听轮庄。
2. 扩展领域类型：新增 `RoundEvent` 或等价页面层模型，保持和牌路径兼容现有 `RoundInput`。
3. 重构算点页状态：引入当前编辑面板、摘要数据、确认弹窗状态。
4. 重做 WXML/WXSS：落地三段式工作台、牌桌区、底部弹层和紧凑摘要行。
5. 接入复用牌选择面板：手牌、和牌张、宝牌、鸣牌逐步迁移。
6. 接入流局事件和结果展示。
7. 运行 `npm run typecheck`、`npm test`、`npm run lint`、`npm run format:check`，并在微信开发者工具中手动验证主路径。

回滚策略：该 change 不涉及持久化 schema 和后台服务；如 UI 重构中途不稳定，可保留旧页面逻辑分支或通过 Git 回退本 change 的页面层改动。

## Open Questions

- 玩家立直状态切换是否在本 change 中完整实现，还是仅保留视觉入口并继续使用手动供托输入？
- 查看记录面板第一版是否只展示最近记录，还是展示所有已保存记录但仅最近一局可回退？
- 底部弹层在小程序真机上是否需要固定高度和内部滚动，避免系统键盘或安全区遮挡？
