## Context

当前系统把荣和建模为单一 `winner` 加单一 `discarder`，页面状态也只有一套手牌、鸣牌、宝牌和场面番型草稿。`riichi` 第三方库负责单手牌番符和基础支付，本场、供托、点数变化和结算记录由项目自己的 `settlement` 模块处理。

一炮多响会跨越 `round`、`settlement`、页面状态、确认弹窗、结果展示和测试。规则口径已在 `docs/riichi-scoring-rules.md` 中确定为雀魂规则：允许双响、三响，积棒和供托上家取り，和牌者中包含亲家则连庄。

## Goals / Non-Goals

**Goals:**

- 支持荣和事件选择 1-3 名和牌者和 1 名放铳者。
- 支持用户按和牌者顺序逐个录入手牌、和牌张、鸣牌和场面番型，并在每名和牌者结算后继续下一名。
- 复用现有单手牌算点能力，对每名荣和者分别算点，再聚合本局支付和点数变化。
- 在多人荣和时按雀魂规则处理积棒、供托和连庄。
- 所有和牌者都计算完成后，保存一次多人荣和结算记录，并支持最近一局返回修改。

**Non-Goals:**

- 不支持包牌责任支付。
- 不支持同一局同时混合荣和和自摸。
- 不支持多人通过联机同步共同输入。
- 不改变第三方 `riichi` 库，也不要求其原生支持多人荣和。
- 不支持自定义地方规则切换；本变更固定采用雀魂规则。

## Decisions

### Decision: 多人荣和作为结算层聚合，不改单手牌算点引擎

每名和牌者仍构造一组 `HandInput` 和单人 `RoundInput`，调用现有 `calculateWithRiichi(handInput, roundInput)`。页面或领域服务收集多个单人 `ScoringResult` 后，交给结算层生成聚合结果。

理由：番符、役种和基础荣和点数对每名和牌者独立成立，现有 adapter 已覆盖这部分；多人荣和的差异主要在支付聚合、本场/供托分配、连庄判断和记录结构。

替代方案是重写算点入口为 `calculateMultipleRon` 并让 adapter 理解所有和牌者。该方案耦合更重，也会让单人算点测试和 UI 调用变复杂。

### Decision: 新增多人荣和事件模型，保留单人事件兼容层

建议引入 `RonWinInput` 和 `MultipleRonRoundInput` 一类结构：

```ts
interface RonWinInput {
  winner: Seat;
  handInput: HandInput;
  roundInput: RoundInput;
}

interface MultipleRonInput extends RoundContext {
  type: "ron";
  discarder: Seat;
  wins: RonWinInput[];
}
```

单人荣和可以视为 `wins.length === 1` 的多人荣和，但实现时可以保留现有 `RoundInput` 路径，降低迁移风险。结算记录层应能表达 `type: "ron"` 且包含 `wins`，结果层应保存每名和牌者的算点结果和聚合支付。

### Decision: 积棒和供托按上家取り归优先和牌者

实现一个纯函数根据放铳者和和牌者列表计算优先和牌者：

```text
东放铳：南 > 西 > 北
南放铳：西 > 北 > 东
西放铳：北 > 东 > 南
北放铳：东 > 南 > 西
```

多人荣和时：

- 放铳者向每名和牌者支付各自荣和点数。
- 积棒收入全部归优先和牌者。
- 供托收入全部归优先和牌者。
- 如果和牌者中包含亲家，则连庄。

这样和雀魂规则一致，也避免供托平均拆分带来的非标准点数展示。

### Decision: UI 使用“选择多个和牌者 + 顺序单人结算”模式

本局事件面板在荣和模式下允许多选和牌者，并要求和牌者不能包含放铳者。选择多个和牌者后，系统按上家取り优先顺序或用户选择顺序提示当前需要录入的和牌者，继续复用现有单人手牌、鸣牌和场面番型录入界面。

用户完成当前和牌者的确认后，系统不立即推进下一局，而是将当前 `HandInput`、和牌条件、单人 `RoundInput` 和单人 `ScoringResult` 暂存到“已完成荣和者结果”列表，并清空或重置牌面输入区，提示继续录入下一名和牌者。直到所有和牌者都完成，系统才聚合支付、点数变化、供托、积棒和连庄结果，生成一条本局结算记录。

共享输入包括场风、局数、亲家、本场、供托、宝牌指示牌、里宝牌指示牌和放铳者。每次单人结算的独立输入包括手牌、和牌张、鸣牌、立直状态、特殊和牌方式、起手役满和附加条件。

这个方案比“多套草稿并行切换”更贴近当前代码：页面仍只需要一套牌面草稿，新增的是多人荣和流程状态：

```ts
interface MultiRonProgress {
  discarder: Seat;
  winners: Seat[];
  currentWinner: Seat;
  completedWins: CompletedRonWin[];
}
```

其中 `CompletedRonWin` 保存当前和牌者的输入快照和单人算点结果。实现时可以在所有和牌者完成前保留编辑态，全部完成后再进入结果页。

### Decision: 最近一局返回修改恢复完整多人草稿

多人荣和结算记录必须保存每名和牌者的输入快照和算点结果。返回修改时优先恢复到多人荣和流程的第一个和牌者，保留已完成结果列表供用户重新逐个确认；重新结算时继续覆盖最近一条记录，而不是追加多条单人记录。

### Decision: 多人荣和进行中回退只操作临时进度

多人荣和进行中状态只存在于临时 `MultiRonProgress`，在所有和牌者完成前 MUST NOT 写入正式 `settlementRecords`，MUST NOT 更新 `playerPoints`，MUST NOT 推进下一局局况。

进行中允许两类回退：

- 回退上一名和牌者：从 `completedWins` 移除最近完成的一项，将该项的输入快照恢复到当前单人输入区，并把 `currentWinner` 指回该和牌者。
- 取消多人荣和流程：清理 `MultiRonProgress` 和当前临时输入，回到普通编辑态，保留当前四家点数和局况不变。

所有和牌者完成并生成正式多人荣和结算记录后，结果页的“返回修改”走最近一局覆盖流程：从记录恢复多人荣和进度和已完成快照，重新逐个确认或重新录入，最后用新的聚合结果覆盖最近记录。

## Risks / Trade-offs

- [Risk] 顺序结算流程比一次性编辑多套草稿步骤更多。→ Mitigation: 在每次单人结算后明确显示“已完成 X/Y，继续结算下一名和牌者”，并保留返回修改入口。
- [Risk] 用户可能误以为第一名结算后已经推进下一局。→ Mitigation: 多人荣和未全部完成前不进入常规结果页，不更新局况和点数，只展示多人荣和进行中状态。
- [Risk] 结果页如果直接拼接多个算点结果会变拥挤。→ Mitigation: 使用按和牌者分组的结果块，聚合点数变化仍放在总览。
- [Risk] 供托/积棒上家取り容易和“每名和牌者各收本场 300”混淆。→ Mitigation: 在结算测试中明确双响、三响的支付明细，并在规则文档和结果文案使用“上家取り”术语。
- [Risk] 单人荣和回归可能被新模型影响。→ Mitigation: 保留现有单人荣和测试，并新增 `wins.length === 1` 等价测试。
